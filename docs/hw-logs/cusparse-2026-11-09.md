## torch sparse through `cfi-run` (PyTorch 2.2.2+cu118, untouched `torch\lib`)

`cfi-run.exe --install-dir <bin> -- python scripts/torch/sparse_check.py`: **129 checks passed, 0 failed**, exit code 0 (23 s cold, 4.7 s warm).
Tolerance 1e-4 (f32) and 1e-10 (f64) relative to max(1, max |CPU|).
Covered, in float32 and float64, for 7x5x3, 64x48x16, 300x200x33, 128x1024x8 (60% dense rows) and 1000x1000x1 with empty rows:
CSR @ dense (contiguous and transposed-contiguous dense), `addmm` with alpha/beta, `mv`, `addmv`, `csr.t() @ dense`, dense @ CSR, `torch.sparse.mm`/`sparse.addmm` and `@` on COO, BSR (4x4 blocks) @ dense and `mv`, `torch.sparse.sampled_addmm`, COO `bmm`, and a GCN-style layer (`relu(A @ (X W))`, 500 nodes).

The redirect log shows `torch\lib\cusparse64_11.dll` requested by full path and served by `<install>\aliases\cusparse64_11.dll` (our `cusparse64_12.dll`).
`CFI_CUSPARSE_TRACE=1` counted 40 SpMV, 174 SpMM, 30 SDDMM and 12 BSR calls: torch uses 32-bit CSR for COO inputs (after `cusparseXcoo2csr`), 64-bit CSR for CSR tensors, and COO descriptors with op(B) = T for `bmm`.

Operations that need entry points the shim does not implement fail with a Python `RuntimeError` naming the call, and the process continues:
`csr + csr` (`cusparseScsrgeam2_bufferSizeExt`), `csr @ csr` (`cusparseSpGEMM_createDescr`), `triangular_solve` with a sparse matrix (`cusparseSpSM_createDescr`), complex64 CSR @ dense (`cusparseSpMM_bufferSize`).
float16 sparse is refused by torch before cuSPARSE is called. Batched (3-D) CSR @ dense is refused by torch's cu118 build itself (`CUDASparseDescriptors.cpp` assert), so the shim's CSR strided batch is covered only by the GPU test above.

Not run: the conda cuda128 torch, performance comparison against the CPU or NVIDIA.
