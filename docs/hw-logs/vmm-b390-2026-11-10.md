(`cargo build --release --locked -p cuda-for-intel`). `scripts/hwvalidate/vmm.ps1 -Ordinals 0` (3 repeats).

So Ollama v0.12.6's exact `ggml_cuda_pool_vmm` sequence works here: the 32 GiB `cuMemAddressReserve` is accepted, the pool grows
across 2 MiB chunks, a kernel spanning chunks is correct, and teardown succeeds.

In the second test, every step before the alias passes: back-to-back chunk mapping, a kernel across chunks, a device copy and a host
copy straddling a chunk boundary. The alias step maps `handles[1]` (already mapped in the pool) at a second reserved range, and
`CUDA_FOR_INTEL_TRACE=1` shows the driver refusing it:

```
CUDA for Intel trace cuMemAddressReserve -> 0
CUDA for Intel trace Level Zero zeVirtualMemMap -> 0x78000004
CUDA for Intel trace cuMemMap -> 1
```

`0x78000004` is `ZE_RESULT_ERROR_INVALID_ARGUMENT`: this driver does not map one physical allocation at two virtual ranges.
CUDA allows that, and GGML's pool does not use it.

Step 2 (stock Ollama with `CUDA_FOR_INTEL_VMM` unset vs `=1`) was not run, because the gate requires step 1 to pass.

Tooling note: under Windows PowerShell 5.1, `vmm.ps1` stops before any test, because `$ErrorActionPreference = 'Stop'` turns cargo's
progress output on stderr into a terminating error. The run above used PowerShell 7.5 (`pwsh -File scripts\hwvalidate\vmm.ps1 ...`),
which does not do that.

## Step 2 attempt: stock Ollama with `CUDA_FOR_INTEL_VMM=1` falls back to the CPU

`scripts/bench-subst-ollama.ps1` clears every `CFI*`, `CUDA_FOR_INTEL*` and `NEO_*` variable before it starts the server
(the `Remove-Item Env:` loop at the top of the per-config block), so `CUDA_FOR_INTEL_VMM=1` set by the caller never reaches Ollama:
four rounds (vmm off/on alternating, `-Configs auto -Runs 3 -Check 12`) all logged `VMM: no` and produced byte-identical text.
Re-run with `scripts/bench-decode.ps1` from #18 instead, which injects the variable per config (Qwen2.5-0.5B-Instruct Q8_0, FA off,
631-token prompt, 48 greedy tokens, 3 servers per setting, interleaved):

| setting | backend in the server log | prefill p50 | decode p50 |
|---|---|---|---|
| `CUDA_FOR_INTEL_VMM` unset (x3) | `library=CUDA`, 25/25 layers on CUDA0, `VMM: no` | 7090 / 7097 / 7138 | 31.1 / 31.4 / 30.8 |
| `CUDA_FOR_INTEL_VMM=1` (x3) | **`library=cpu`, CPU model buffer, no GPU device found** | 2484 to 2672 | 110 to 157 (CPU numbers) |

Output text equals the CPU backend in all six servers, because the VMM servers *are* the CPU backend. With `OLLAMA_DEBUG=1`, the
`cuda_v13` discovery probe returns no device after 285 ms and its driver log stops right after cudart's runtime integrity check;
with VMM unset the same probe finds the B390.

Cause, reproduced without Ollama (`ctypes` against this branch's `nvcuda.dll`, `CUDA_FOR_INTEL_VMM=1`):

```
cuInit 0
cuDeviceGetAttribute(102 VMM) 0 value 1
granularity, no current context -> (201, 0)
cuDevicePrimaryCtxRetain 0
granularity, primary ctx retained but not current -> (201, 0)
cuCtxSetCurrent 0
granularity, primary ctx current -> (0, 2097152)
```

`cuMemGetAllocationGranularity` runs inside `with_context` and returns `CUDA_ERROR_INVALID_CONTEXT` without a current context.
CUDA answers it from the device alone, and `ggml_cuda_init` calls it (under `CU_CHECK`, which aborts) for every device that
advertises VMM, before any context is current; the discovery probe aborts and Ollama falls back to the CPU. The gate tests create
a context first, so they do not catch it. VMM must stay off until the granularity query (and the other device-level queries) work
without a current context, for example from the device's primary context or a per-device Level Zero context.
