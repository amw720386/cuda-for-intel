# Running PyTorch on an Intel GPU

Verified on Windows x64, Intel Arc B390, results compared with the CPU. Evidence:
`docs/torch-bringup.md`, `docs/hw-logs/torch-round1.md`, `docs/torch-arch-guard-stubs.md`.
Other GPUs, Linux and other PyTorch versions are untested.

## Which builds can work

The shim translates PTX and never executes SASS, so PyTorch must ship PTX in its CUDA fatbins
(checked by scanning `.nv_fatb` in the DLLs).

| Build | PTX in the wheel | Status |
| --- | --- | --- |
| Windows wheel `torch 2.2.2+cu118` (`download.pytorch.org/whl/cu118`) | compute_37, ISA 7.8 | works |
| conda-forge `pytorch 2.13.0` build `cuda128` (micromamba, `CONDA_OVERRIDE_CUDA=12.8`) | compute_120, ISA 8.7 | works |
| Windows wheels cu121 to cu130 (2.1 to 2.9; the log also scanned 2.11.0 cu128, 2.14.1 cu126 and a cu130 wheel) | none, SASS only | cannot run |
| Linux wheels cu129 / cu130 | compute_120 | not tried (no Linux GPU host) |

## Staging

1. Create a venv (cu118) or a micromamba environment (cuda128) in a directory you own. Install nothing into system locations.
2. Build: `cargo build --release --locked -p cuda-for-intel -p cublas_shim`.
3. Load this project's `nvcuda.dll` **before** `import torch`, with `ctypes.WinDLL(r"C:\cfi\bin\nvcuda.dll")`.
   A module already loaded under the name `nvcuda.dll` satisfies later by-name loads.
4. In torch's `lib` directory keep `*.orig` copies and replace the CUDA math libraries with the built `cublas64_12.dll`:
   - cu118: install it as `cublas64_11.dll` and as `cublasLt64_11.dll`;
   - cuda128 / CUDA 12: as `cublas64_12.dll` and `cublasLt64_12.dll`.

   Windows resolves every import at load time, so the shim exports NOT_SUPPORTED stubs for all other cuBLAS names the wheel's DLLs import
   (generated by `scripts/torch/gen_cublas_stubs.py` from the wheel's export list; the generated `crates/cublas_shim/src/stubs.rs` is committed).
   If a new wheel imports names that are missing, `import torch` fails with an unresolved import: regenerate the stubs.
5. Set `CUDA_FOR_INTEL_HYBRID_DIR` to a directory holding the signed `nvcudart_hybrid64.dll` (see `docs/ollama.md` for hash and source;
   not bundled, you obtain it yourself). Set `CUDA_MODULE_LOADING=LAZY`.
6. In your program: `torch.backends.cudnn.enabled = False` (there is no cuDNN backend; convolutions use ATen's native kernels).

## Compute capability and attention (SDP) settings

PyTorch's wheels compile some kernels (the CUTLASS memory-efficient attention `fmha_cutlassF_*`) to an empty, `vprintf`-only body for the PTX
architecture they ship, because the code is guarded by `#if __CUDA_ARCH__ >= 750`. Running such a stub computes nothing.
The runtime therefore does two things:

- **Loud failure.** A lazily translated kernel whose body has no loads, stores, atomics, barriers, `cp.async`, `mma` or texture/surface ops is rejected
  with `CUDA_ERROR_NO_BINARY_FOR_GPU` (209); PyTorch prints `no kernel image is available for execution on the device`.
  `CFI_ALLOW_EMPTY_KERNELS=1` restores the silent behaviour (do not use it for real work).
- **Reported compute capability.** The runtime reports a capability that steers PyTorch to real kernels. Defaults by process (commit `4e29240`):
  `torch_cuda.dll` with `cudart64_110.dll` (cu118 wheels): 3.7; `torch_cuda.dll` with `cudart64_12.dll` (conda CUDA 12 builds): 12.0;
  every other process: 7.5. `CFI_REPORT_CC=<major>.<minor>` always wins.

Measured with an explicit `CFI_REPORT_CC` (`docs/torch-arch-guard-stubs.md`, Arc B390, default SDPA, MultiheadAttention and TransformerEncoderLayer vs CPU):

| Build | `CFI_REPORT_CC` | Result |
| --- | --- | --- |
| cu118 | 7.5, 7.0, 5.0 | stub kernel chosen, loud 209 |
| cu118 | 3.7 | correct (PyTorch uses the math path) |
| cuda128 | 7.5 | sm75 stub selected, loud 209 |
| cuda128 | 8.0 or 12.0 | `fmha_cutlassF_*_sm80` selected, correct |

The automatic per-process profile was added after those measurements and is described by its commit; the table above is what was measured
by setting the variable explicitly. If you see error 209 in attention, set `CFI_REPORT_CC=3.7` (cu118) or `12.0` (cuda128), or keep the default
capability and switch the fused backends off in your program:

```python
torch.backends.cuda.enable_mem_efficient_sdp(False)
torch.backends.cuda.enable_flash_sdp(False)
```

## What worked (cu118, compared with CPU)

zeros, add, matmul in all transposes, bmm, Linear forward and backward, relu / gelu / softmax / layer_norm / sum, conv2d forward and backward,
max_pool, embedding, index_select, cat, fp16 cast and autocast matmul, rand / randn / dropout (ATen Philox), batch_norm,
SGD / Adam / AdamW (foreach included), TransformerEncoderLayer forward and all gradients, events, streams, pinned non-blocking copies, `memory_stats`.
cuda128: matmul, Linear, softmax, layer_norm, gelu, sum, conv2d forward and backward, SDPA math, randn, autocast fp16 and an SGD training loop.

## Known gaps

- Two `complex<double>` foreach kernels do not translate. About 6 % of the entries in the probed cuda128 modules still fail
  (listed in `docs/torch-bringup.md`), and 61 of 308 cuda128 ATen modules were too large to probe within 15 minutes each.
- cuDNN, NCCL, cuFFT and cuSOLVER paths are unavailable. The first use of a very large module takes tens of seconds
  (the translation cache removes this on later runs).
- At process exit you may see `cuLibraryUnload 999` after Level Zero teardown; it is harmless.

## Probing kernels

`tests/ptx_corpus/harness` (`ptx-corpus-harness --probe module.ptx`) translates every entry of a module on its own and groups failures;
dump modules first with `CFI_PTX_DUMP_DIR=dir`. It builds on macOS.
